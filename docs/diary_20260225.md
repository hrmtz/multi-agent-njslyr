## エピソード11: ヤクザ天狗爆誕 — 設計して3時間で実戦投入

### 11-1: なぜ天狗が必要だったのか

ネオサイタマのマルチエージェントシステムには致命的なボトルネックがある。**グレーターヤクザの過労死**だ。

グレーターヤクザ（本日より「ヤマヒロ」と命名された）は、7体のクローンヤクザへのタスク分解・配信・QC判定・ダッシュボード更新を一手に担う中間管理職AIである。クローンヤクザが7体同時に完了報告を上げると、ヤマヒロのinboxに未読が7件溜まる。コンテキストウィンドウが逼迫し、処理が追いつかず、最悪の場合コンテキスト枯渇で過労死する。

過去の記録では、ヤマヒロは深夜に6時間以上ダウンし、ダークニンジャ（司令塔）不在の中で単独統治を強いられたこともある。中間管理職1体に全負荷が集中する設計は、明らかに限界だった。

解決策として設計されたのが**ヤクザ天狗**である。

### 11-2: 天狗の仕様

ヤクザ天狗は「常駐しない一時的な副監督」として設計された。仕様はこうだ:

- **spawn条件**: ヤマヒロのinbox未読が5件以上になると自動発動
- **宿主**: アイドル中のクローンヤクザ1体を乗っ取る（最もアイドル時間が長い個体を選択）
- **モデル**: Claude Sonnet（軽量・高速。監視業務にOpusは過剰）
- **識別**: ペイン背景色がダークピンク（#3a0025）に変わる。通常ヤクザの黒、バリキドリンク投与中の紫とも異なる第3の色
- **despawn条件**: ヤマヒロのinbox未読が2件以下に戻ると自動消滅。宿主ヤクザは元のモデル・元のタスクに復帰する
- **上限**: 4時間で強制despawn（居座り防止）

### 11-3: 3体Opusの相互批判設計

実装にあたり、ヤマヒロはOpus 3体による**相互批判方式**を採用した。

- **yakuza4（案A: 堅牢性重視）**: ガード条件を徹底的に入れる石橋叩き型。「全入力を信用するな」

採用されたのは**案B基盤に案Aのガード条件と案Cのテスト設計を統合**した折衷案。MUST要件11件、SHOULD要件5件、batsテスト13件の仕様が確定した。

## エピソード12: バリキドリンクの処方箋 — 投与・効果・解毒・そして失態

### 12-1: バリキドリンクとは何か

クローンヤクザは通常、Claude Sonnet（軽量・高速モデル）で稼働している。しかし高難度タスクに直面したとき、Sonnetのカラテでは足りないことがある。

そこで投与されるのが**バリキドリンク**である。

```bash
inject_barikidorink "multiagent:1.2"
```

このコマンドを実行すると:

1. `/model opus` — モデルをClaude Opus（最高性能）に切り替え
2. ペインの背景色が**毒々しいパープル（#1a002e）**に変わる
3. `/clear` — セッションをリセットし、新しいモデルで再起動

黒いペインの中に1体だけ紫色に光るヤクザが現れる。禁断の薬物でブーストされた姿そのものである。

権限は委譲する。だが責任も委譲する。ネオサイタマの薬事法は実に合理的である。

## エピソード13: オートコンプリートの罠 — 0.3秒の隙を突かれて

本日修正されたバグの中で最も地味だが最も厄介だったのがこれだ。

エージェント間通信において、inbox_watcher.shがtmux send-keysでスリケン（通知メッセージ）を投げる。テキストの送信とEnterキーの送信は別々のコマンドで、間に0.3秒のスリープを挟んでいた。

```bash
tmux send-keys -t "$PANE" "$text"
sleep 0.3
tmux send-keys -t "$PANE" Enter
```

この0.3秒の隙をClaude Codeのオートコンプリートが突く。テキスト入力の瞬間に補完候補メニューが表示され、0.3秒後のEnterが「補完候補の選択」として食われる。スリケンは届かず、エージェントは永遠にアイドルのまま。

ヤマヒロにチョップ（/clear）を送った際もこのバグが発動し、/clearがオートコンプリートに食われてヤマヒロが起きないという事態が発生した。

修正: テキストとEnterを1コマンドに統合。ただしCodex TUI（別のCLIツール）では逆にこれだと壊れるので、CLI種別で分岐が必要。0.3秒の間合いが生死を分ける、tmux格闘術の奥義である。
